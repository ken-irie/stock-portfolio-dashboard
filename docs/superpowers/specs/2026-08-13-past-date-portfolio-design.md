# 過去日ポートフォリオ表示 設計

作成日: 2026-08-13
対象リポジトリ: `stock-portfolio-dashboard`（公開リポジトリ）
前提となる設計: `2026-08-13-supabase-portfolio-sync-design.md`

## 1. 背景と目的

Supabase連携により、日次のスナップショット（日付・資産残高・元本）と保有明細がDBに蓄積されるようになった。しかし現在の画面は、明細を保存するだけで読み戻さない。ポートフォリオ（ドーナツ・銘柄一覧）は起動時つねに空で、CSVを読み込まないと何も表示されない。

そこで日付セレクタを設け、選んだ日のポートフォリオをDBから復元して表示する。

- 過去のある日にどの銘柄をいくら持っていたかを振り返れる
- 起動しただけで直近のポートフォリオが見える（毎回CSVを探さなくてよい）
- 別のPCでも、CSVを持ち歩かずに中身を確認できる

## 2. 前提と決定事項

| 項目 | 決定 |
|---|---|
| 日付の選び方 | セクション見出しに置く日付セレクタ |
| 起動時 | DBの「明細のある最新日」を自動表示する |
| 明細が無い日 | セレクタに出し「（明細なし）」と表記する |
| 明細の取得 | 日付を選ぶたびにDBから取得する（キャッシュしない） |
| 「現在」という状態 | 作らない |

### 明細を都度取得する判断について

起動時に全日分をまとめて取得する案もあったが、採らない。現時点で12日×約40銘柄＝約500行だが、毎日記録すれば1年で1万行を超える。起動時に取るデータの大半は結局見ない日のものになる。

一度見た日をメモリにキャッシュする案も採らない。キャッシュはCSV再読込やDB更新とずれる余地を持ち込む。日付切り替えは連打する操作ではないので、まず都度取得で作り、実際に重ければ後からキャッシュを足す。3行で足せるものを先回りする理由がない。

### 「現在」という状態を作らない判断について

CSVを読み込んだ日付はDBにも保存されるため、セレクタでその日を選ぶことと等価になる。「現在」と「過去日」を別の状態として持つと、両者の切り替え・不整合・戻り方をすべて設計する必要が出る。状態をひとつ減らし、日付という単一の軸に統一する。

## 3. UIと操作

### 3.1 日付セレクタ

セクション見出しの行に置く。「いまどの日付を見ているか」はポートフォリオそのものの属性であり、この見出しが自然な置き場である。

```
資産ポートフォリオ (全て)  [2026-08-13 ▼]  評価額順 [降順]
```

選択肢は新しい日付が上。明細の無い日は区別できるようにする。

```
2026-08-13
2026-08-12（明細なし）
2026-08-07（明細なし）
2026-08-03（明細なし）
2026-07-25
2026-07-22
…
```

### 3.2 各操作での挙動

| 操作 | 挙動 |
|---|---|
| 起動時 | 推移を取得しセレクタを構築。**明細のある最新日**を選んで表示する。全体の最新日ではないのは、最新が明細なしだと開いた瞬間に空の画面が出るため。明細のある日が1つも無ければ従来どおり空 |
| 日付を選ぶ | その日の明細を取得して表示。推移カードの詳細バーも同じ日付に同期する。アプリバーの読み込み状況表示 `#src` を `2026/07/16 の記録（Supabase）` に更新する |
| CSV読込 | これまで通りその内容を表示し、セレクタをその日付に合わせる。表示はすでにCSVの内容なのでDBから取り直さない。`#src` は従来どおりファイル名と基準日を出す |
| リセット | 表示を空にし、`#src` を `CSV未読み込み` に戻す。セレクタは先頭に置いた空の選択肢（`—`）を選択状態にする |
| Supabase未設定 | セレクタを描画しない。アプリは現在とまったく同じ挙動 |

推移カードの詳細バーを同期させるのは、2つのカードが別々の日付を指す状態を作らないため。既存の `histShow()` を1行呼ぶだけで済む。

### 3.3 明細が無い日を選んだとき

銘柄一覧の位置に案内文を出す。

> この日の保有明細は記録されていません。金額は上の資産推移で確認できます。

サマリー（資産残高・元本・損益）を推移の記録から別途組み立てることはしない。金額は推移カードの詳細バーに出るため、表示経路を二重に持たない。

## 4. スキーマ変更

セレクタで「明細なし」を出すには、日付ごとに明細があるかを知る必要がある。3つの方法を検討した。

1. `holdings` を全件取得して日付を重複除去 — 1年運用で1万行以上を毎回転送することになり、日付を知るコストとして高すぎる
2. PostgRESTの集計関数 — 追加設定に依存し、環境によって動作が変わる
3. `snapshots` に件数列を持たせる — すでに起動時に取得している推移データに1列増えるだけで、クエリは増えない

3を採る。`holdings` を書くのはこのアプリだけなので、件数がずれる余地はほぼない。

```sql
alter table snapshots add column holdings_count integer not null default 0;

-- 既存の行を埋め直す
update snapshots s
set holdings_count = (select count(*) from holdings h where h.snapshot_date = s.snapshot_date);
```

## 5. モジュール構成

### 5.1 supabase.js（公開6関数 → 7関数）

| 関数 | 変更 |
|---|---|
| `sbSaveSnapshot` | upsertのbodyに `holdings_count: rows.length` を追加。件数を先に知る必要があるため、**明細配列の組み立てを関数の冒頭へ移す**（try/catchごと前倒し）。リクエストの順序（upsert → 明細DELETE → 明細INSERT）は変えない |
| `sbLoadHistory` | selectに `holdings_count` を足し、戻り値を `{date, total, cost, n}` に拡張。既存の呼び出し側は `n` を無視するため影響しない |
| `sbLoadHoldings(date)` | **新規。** `GET /holdings?snapshot_date=eq.<date>&select=name,code,broker,acct,cat,qty,value,cost`。行の配列を返し、失敗時は `null` |

`sbLoadHoldings` の戻り値は `RAW` と同じ形なので `setData()` にそのまま渡せる。セクター分類・証券会社別の内訳も現在と同じ経路で処理される。

### 5.2 app.js

| 追加するもの | 役割 |
|---|---|
| `buildDateSelector(hist)` | 推移データからセレクタの選択肢を作る。新しい順、`n===0` に「（明細なし）」を付ける |
| `showDate(date)` | その日の表示に切り替える。明細取得・`setData()`・詳細バー同期・見出し更新 |
| `hydrateFromDB` の拡張 | 推移取得後にセレクタを構築し、明細のある最新日を表示する |
| `rebuildFromLoaded` の末尾 | CSV読込後にセレクタを作り直し、その日付を選択状態にする |
| リセット処理 | セレクタを未選択に戻す |

## 6. データフロー

### 6.1 起動時

```
sbLoadHistory()
  → localStorageを更新（既存の動き）
  → buildDateSelector(hist)
  → n>0 の最新日を選び showDate(date)
```

### 6.2 日付を選んだとき

```
showDate(date):
  n===0 → 表示を空にし、一覧の位置に案内文
  n>0   → sbLoadHoldings(date) → setData(rows)
  共通  → histShow(その日の推移エントリ)
        → #src を「2026/07/16 の記録（Supabase）」に更新
```

### 6.3 連打による表示の入れ替わりの防止

セレクタは素早く連続で変更できるため、**古いリクエストが後から返って新しい表示を上書きする**競合が起こりうる。

これは本プロジェクトで既に2回発生した競合と同じ構造である（起動時の読み戻し対CSV読込、および起動時の読み戻し対履歴クリア）。どちらも後から発見して修正した。同じ形だと分かっている以上、最初から防ぐ。

リクエストごとに連番を持ち、**発行時の番号が最新であるときだけ結果を反映する**。

```
let showSeq=0;
async function showDate(date){
  const seq=++showSeq;
  const rows=await sbLoadHoldings(date);
  if(seq!==showSeq) return;   // より新しい選択が始まっている
  …
}
```

## 7. エラー処理

| 状況 | 挙動 |
|---|---|
| Supabase未設定 | セレクタを描画しない。アプリは現在と同一 |
| 起動時の推移取得に失敗 | セレクタを作らず、localStorageの推移でグラフだけ描く。表示は `DB同期失敗`。ポートフォリオは従来通り空 |
| 日付選択後の明細取得に失敗 | **表示は変えずに直前の内容を維持**し、セレクタの選択も元の日付に戻す。`DB同期失敗` を出す。中途半端に空になるより、見えていたものが残る方が安全 |
| `holdings_count > 0` なのに明細が0件で返る | データ不整合。「明細なし」と同じ案内文を出す |

## 8. スコープ外（YAGNI）

- 明細のメモリキャッシュ — 都度取得で作り、重ければ後から足す
- 2日分を並べて比較する差分表示
- 過去日の明細の編集・削除
- 明細なしの日にサマリーを別経路で組み立てること

## 9. テスト方針

### 9.1 `test/supabase.test.html` に追加（現在29件）

- `sbLoadHoldings`: URLとselect句が正しい
- `sbLoadHoldings`: 戻り値が `RAW` と同じ形の配列になる
- `sbLoadHoldings`: 失敗時に `null` を返す
- `sbLoadHoldings`: 未設定時は `fetch` を呼ばず `null` を返す
- `sbLoadHoldings`: 空配列と `null` を区別できる
- `sbLoadHistory`: `holdings_count` を `n` として返す
- `sbSaveSnapshot`: upsertのbodyの `holdings_count` が明細件数と一致する
- `sbSaveSnapshot`: 明細に不正な行があるとき、**1度も通信せずに** `false` を返す（組み立てを冒頭へ移した影響を固定する）

### 9.2 app.js側（iframeハーネス）

テストランナーが無いため、キャッシュを迂回したiframeにスタブを注入して確認する。

- 履歴からセレクタが正しく構築される（新しい順、`n===0` に「（明細なし）」）
- 起動時に「明細のある最新日」が選ばれる（最新が明細なしでも空にならない）
- 日付変更で正しいURLを叩き、ドーナツと銘柄一覧が入れ替わる
- 明細なしの日で案内文が出る
- 連続で切り替えても、最後に選んだ日付の内容が表示される（古い応答が勝たない）
- 明細取得に失敗したとき、直前の表示が維持される
- Supabase未設定でセレクタが出ず、既存動作が変わらない

### 9.3 実データでの確認

`holdings_count` の埋め直しSQLを流した後、既存の日付でセレクタの表記が実態と合っているかを目視する。
